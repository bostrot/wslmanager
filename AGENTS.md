# WSL2 Distro Manager — Agent Instructions

## What This Is
Flutter desktop app for managing WSL distributions on Windows x64 (primary target), with a native macOS port that manages Linux/macOS VMs through Apple's Virtualization.framework instead. Uses Provider for state management and `fluent_ui` for Windows-native UI.

**Required setup:** `flutter config --enable-windows-desktop` (Windows) / `flutter config --enable-macos-desktop` (macOS)

**macOS dev runs need a signed `vmctl` first.** VMs are created by the Swift
helper, not by the Flutter app, and Virtualization.framework only answers a
process holding `com.apple.security.virtualization`. `swift build` signs its
output ad-hoc with `get-task-allow` alone, so the helper has to be re-signed
with `macos/vmctl/vmctl.entitlements` — which is what `VMCTL_ONLY=1
scripts/build_macos.sh` does, installing the result to `~/Library/Application
Support/WSLManager/bin/vmctl`. That path sits ahead of the repo's `.build/`
output in the `findVmctlHelper` candidate chain
(`lib/api/apple/apple_vm_api.dart`), so an install is what keeps a debug run off
the unsigned binary. Miss it and the app starts normally but every VM start
fails with `VZErrorDomain Code=2 "The process doesn't have the
"com.apple.security.virtualization" entitlement."`. **Re-run it after any change
under `macos/vmctl/`** — `flutter run` rebuilds Dart only, so an edited helper is
silently the old one. `helperPath()` re-resolves per call, so a running
`flutter run` session picks up a freshly installed helper without a restart.

## Testing
- Tests in `test/` cover WSL, Docker images, templates, paths, etc.
- WSL-dependent tests create/delete real distro instances; require WSL available
- `test/mocks.dart` has shared mock utilities (MockShell, MockHttpClientAdapter, etc.)
- Integration tests in `integration_test/` simulate clicking through the app UI (navigation, dialogs, license screen, AI panel, AI Workspace, settings)
- Use `ValueKey('test-*')` keys on widgets that need to be found by e2e tests
- **`ValueKey`s must be unique per list item**, not hardcoded per widget-shape. A shared literal key across N repeated widgets (e.g. one `Button` per card in a list) causes `find.byKey()` to throw "ambiguously found multiple widgets" once all N are simultaneously mounted — this can stay hidden for a long time if the widgets are gated behind a loading state during earlier testing, then surface the moment that loading is fixed/sped up. Prefer `ValueKey('test-foo-${item.id}')`.
- **Integration test setup:** Always initialize `prefs = await SharedPreferences.getInstance()` in `setUp()` before pumping the widget
- **`MockShell.run()` (`test/mocks.dart`) matches on `arguments.contains(...)` and positional indices** (`arguments[1]`, `arguments[2]`, …), and ignores the `executable` parameter entirely. This breaks for SSH-wrapped remote calls, since `ssh` prepends ~10 option tokens before the real subcommand, shifting every position. New remote-path tests should assert via `.contains(...)` only — never rely on positional indexing — or extend the mock to be SSH-shape-aware (locate `--` and index relative to it).
- **`Notify.message`** (`lib/components/notify.dart`) is a `static late Function` with no default value or initializer. Any code path under test that calls it — including service/API-layer code, which is an accepted pattern here (see `lib/api/templates.dart`, `lib/components/sync.dart`, `lib/api/ai_workspace/service.dart`) — throws `LateInitializationError` unless the test stubs it first: `Notify(); Notify.message = (msg, {duration, severity = InfoBarSeverity.info, loading = false, useWidget = false, leadingIcon = true, dynamic widget}) {};` in `setUpAll()`. The stub is typed (`NotifyMessage` in `notify.dart`), so it must name **every** parameter — a stub missing one fails to assign at compile time, which is the point.
- **Integration tests run via `LiveTestWidgetsFlutterBinding`** (`flutter test integration_test/foo.dart -d windows` — a real windowed app, not a synthetic canvas). `tester.view.physicalSize`/`devicePixelRatio` overrides do **not** affect layout here the way they do in standard widget tests — the real window's current size/DPI scaling governs layout, and can't be forced from the test. Don't write assertions that depend on display-mode breakpoints (e.g. fluent_ui's compact/open threshold) being controllable this way.
- **Long/looping `flutter test ... -d windows` runs can have their output silently truncated** by tool-output capture on multi-failure runs. When debugging, redirect to a file (`... > out.txt 2>&1`) and read the file directly rather than trusting truncated tail output.
- **macOS integration tests run one file at a time** (`flutter test integration_test/<file>.dart -d macos`): pointing at the whole directory only runs the first file — every later file times out at load on desktop devices. `ai_workspace_test.dart` self-skips on macOS (the feature is WSL-only). No `sudo xcode-select` needed: export `DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer` and xcodebuild/xcrun/flutter follow it.
- **Integration tests that tap anything MUST seed `{'version': currentVersion, 'LastChangelogVersion': currentVersion}` into the mock prefs.** With empty prefs, `initRoot` sees a first start and opens the welcome dialog; its ModalBarrier then swallows *every* synthesized tap for the rest of the test — silently, because the taps are all `warnIfMissed: false` and a hit test still "succeeds" (against the barrier). Diagnosed live 2026-09-01 on macOS: the arena for a tap on the MCP toggle contained only the barrier's `_AnyTapGestureRecognizer`, and directly invoking the toggle's `onChanged` worked while the tap did not. If a tapped control mysteriously doesn't react in an integration test, check for an open dialog before suspecting the widget.

## Community catalogue (`cdn/scripts.json`)
- The catalogue lives on the **`catalogue` branch** (`cdn/scripts.json`, nothing else of note), and the app reads it raw from `raw.githubusercontent.com/bostrot/wsl2-distro-manager/catalogue/cdn/scripts.json` — no proxy, nothing to keep running. It used to be committed to `main` and served by GitHub Pages (which still serves `main`'s root at `wslmanager.bostrot.com`, e.g. `doc/api`), but `main` requires a pull request and on a personal repository the workflow token cannot bypass that, so the daily push was rejected. Never point the workflow back at `main`.
- **Never build that catalogue on the client.** The Community screen used to list `scripts/` in `bostrot/wsl-scripts` and then fetch `info.yml` for each of its ~80 folders, plus a commits call each for the "updated" line: 161 sequential requests, 81 of them against `api.github.com`, where an anonymous caller gets **60 an hour shared with everyone behind the same address**. It was slow for the lucky and rate-limited for the rest.
- `.github/workflows/community-catalogue.yml` runs `scripts/build_community_catalogue.dart` daily (04:17 UTC — outside the 08:00–20:00 commit window) from `main`, with the `catalogue` branch checked out beside it, and pushes `cdn/scripts.json` there only when it changed. The output carries no timestamp of its own precisely so an unchanged day produces a byte-identical file and no commit. `bostrot/wsl-scripts` can push it early with a `repository_dispatch` of type `community-scripts-updated`.
- The generator imports **dart:io and dart:convert only**, so CI runs it with `dart-lang/setup-dart` and no `pub get`; its pure functions are covered by `test/build_community_catalogue_test.dart` the same way `check_store_listing.dart` is.
- `CommunityScripts.list()` falls back to the old per-folder walk, and `App.getDistroLinks()` falls back to raw GitHub then the bundled asset. Keep those: an earlier n8n webhook served `200` with an **empty body**, which the app read as "no data" and silently answered from a build-time copy for days.

## Distro catalogue (`images.json`) and CPU architecture
- Each entry maps an **architecture to a URL** — `{"x64": "…", "arm64": "…"}` — because WSL does not emulate: on a Windows-on-ARM PC an x86-64 root filesystem imports fine and then cannot run a single binary (`bostrot/wsl2-distro-manager#229`). A distro that publishes only one architecture lists only that one and is left out of the list on the other; an entry that cannot run is worse than a missing one, since the user only finds out after a few hundred megabytes and an `exec format error`.
- The old flat `"name": "url"` form still parses, matched by the architecture named in the URL, because **the CDN copy is uploaded by hand** and lags the repo's own. A source whose entries are all for the other architecture counts as unusable, so such a machine falls through to raw GitHub (the repo's `images.json`) instead of being shown an empty list. Upload the new shape when convenient; nothing breaks until then.
- `lib/api/rootfs_architecture.dart` owns "which architecture does the next distro need" (`rootfsHostArchitecture`) and the catalogue reduction (`rootfsLinksFor`). It reuses `cloudLocalArchitecture` from the cloud deploy, which already handles the case that matters: the Windows build is x64 only, so on an ARM64 PC it runs **emulated** and its own ABI lies — `PROCESSOR_ARCHITEW6432` is what tells the truth. With a remote WSL host, or off Windows, the architecture is unknowable and the x64 entries are served.
- Docker imports go through the same family: `manifestForArchitecture` picks the manifest for this machine (and skips the Windows entries a tag often also carries) where the code used to take `amd64` unconditionally.
- Adding a distro: check the mirror actually publishes an arm64 WSL/rootfs tarball (SLES and Arch do not, as of 2026-09) and keep the URL under the key that matches it — `test/rootfs_architecture_test.dart` fails on a URL filed under the wrong architecture.

## Release Pipeline (`.github/workflows/releaser.yml`)
- Triggers on push to any branch matching `lib/`, `assets/`, `windows/`, `installer/`, `LICENSE`, or `pubspec.yaml`
- Produces: ZIP archive, MSIX, and Inno Setup `.exe`, for x64 and (from `build-arm64`) Arm64
- On `main` only: creates a GitHub release with tag, then triggers winget/scoop/store publish workflows — from the separate `publish` job, which waits for the Arm64 build so the WinGet manifest is generated once both installers are attached, and still runs (`always()`) when that build failed
- **The Windows Arm64 build (`build-arm64`).** There is no cross compile: on Windows the Flutter tool targets the architecture of the *Dart executable running it*, which is why the job runs on `windows-11-arm` and why it must not use `subosito/flutter-action`. Flutter publishes no Arm64 SDK for Windows (`releases_windows.json` is x64 only), so the action would unpack the x64 zip, its `dart.exe` would run under Prism emulation, and the build would quietly produce the x64 app again under an Arm64 filename. Cloning the SDK at the pinned tag runs `bin/internal/update_dart_sdk.ps1`, which downloads the native Arm64 Dart SDK when `PROCESSOR_ARCHITECTURE` says `ARM64`. Because *every* step downstream of that mistake succeeds, the job asserts on the PE header (`scripts/check_pe_architecture.dart`, `IMAGE_FILE_MACHINE_ARM64` = `0xaa64`) before anything is packaged. The two Flutter pins are deliberately different — `windows-arm64` engine artifacts only exist from **3.44.0** on, so the 3.41.6 the x64 release ships from cannot build this at all; `test/windows_arm64_pipeline_test.dart` fails if `FLUTTER_ARM64_VERSION` drops below that. Output lands in `build/windows/arm64/runner/Release`, the MSIX comes from `dart run msix:create --architecture arm64`, and `installer/setup.iss` takes a `TargetArch` define (`x64` → `x64compatible` and the old filename, so nothing changes for x86; `arm64` → `ArchitecturesAllowed=arm64` and `-arm64-setup.exe`). Same `AppId` in both, so either installer upgrades the other in place. The Arm64 assets follow `macos.yml`'s rule below — attached only to a release this run created, never `--clobber` — for the same checksum reason.
- **Store pricing and `publish-store.yml`.** Microsoft's legacy submission API cannot read a product on "Pricing Version 2" (any price edited in the Partner Center UI; the page then shows *Review price per market*): it returns `priceId: "Base"`, and a publish that echoes that back made the app Free in all 240 markets on 2026-09-07/08. Microsoft's own `msstore-cli` has the same bug open (#112) and now refuses with "App updates are supported only for Free products"; support's word is "by design". So: (1) without `pricing_file` the script refuses on `"Base"` and never deletes a pending submission — update the MSIX by hand in Partner Center then; (2) the durable route is **pricing as code**: `store/pricing.json` states the base tier and per-market tiers in the API's own terms (`scripts/store_pricing.jq` merges it into the clone, keeping NotAvailable markets), the workflow's `mode=dry-run` proves the round trip without uploading or committing, and only then should a release pass `pricing_file`. After that, **edit prices in the JSON, never in the UI** — a UI edit flips the product back to Version 2. Tier ids are positions in Partner Center's tier table (Tier1012 = USD 0.99): Tier1052 = 4.99, Tier1102 = 9.99, Tier1112 = 14.99. `scripts/test_store_pricing.sh` checks the merge offline. The releaser triggers this workflow by `workflow_dispatch` with only `tag`, so releases keep the refuse-on-Base behaviour until that call passes `pricing_file`.
- Nightly artifacts uploaded on every run regardless of branch
- **The Homebrew casks and `macos.yml`.** Two casks serve `wsl-manager`: `Casks/wsl-manager.rb` in `bostrot/homebrew-tap` (not here, because `brew tap bostrot/tap` resolves by name; `scripts/update_homebrew_cask.sh` keeps it pointing at the bytes the release serves, and `scripts/test_homebrew_cask.sh` exercises it offline against a fake `gh`), and `Casks/w/wsl-manager.rb` in Homebrew's own `homebrew/cask`, which BrewTestBot bumps within hours of a tag and which a plain `brew upgrade wsl-manager` resolves — nothing in this repository can rewrite it. The failure to understand is not a cask drifting on its own: a rebuild on `main` that re-uploads the dmg under a tag that is *already released* changes the checksum of that download under a cask that cannot follow, and every `brew upgrade` then dies with "Cask reports different checksum" until the next version. That broke 2.0.2 for the tap on 2026-09-09 (`bostrot/ai-tasks#63`, expired `HOMEBREW_TAP_TOKEN`) and 2.3.0 for the official cask on 2026-09-17 (a main push two hours after the tag). So the attach step in `macos.yml` treats a released dmg as immutable: it uploads the mac assets only when the release carries none yet, never with `--clobber`, and never from an unsigned build. Later builds of the same version only ship as nightly artifacts; a bad release asset is replaced by hand together with a version bump. `update` still reads the cask back after the write rather than trusting the PUT, and when the token expires the fix is a new one with `contents:write` on the tap.

## fluent_ui Gotchas
- **Icons:** `FluentIcons.sparkle` does not exist — use `FluentIcons.flag` or `FluentIcons.star` instead
- **`_solid`/`_fill` icon variants are risky:** e.g. `crown_solid`, `lightbulb_solid` are declared in the Dart bindings but may not exist in the bundled `FluentIcons.ttf` subset, rendering as a blank/tofu glyph. Before using a `_solid`/`_fill` variant, grep the codebase for existing usage as proof it renders — as of this writing there is none anywhere in `lib/` (the only prior example, `heart_fill`, lived in the dead `lib/components/navbar.dart`, deleted 2026-08-28). Prefer the base variant (`crown`, `lightbulb`, …) unless you can visually confirm the solid one renders.
- **`PaneItem.title` must be a literal `Text` widget**, never a `Row`/composite. fluent_ui extracts the label via a `Text`-only property getter (`getProperty<String>()`); a non-`Text` title silently renders as an empty box — icon only, in *every* display mode, no error. Put badges/pills (e.g. a "NEW" tag) in `PaneItem.infoBadge`, not inside the title widget.
- **`PaneDisplayMode.auto` only shows labels (open mode) at window width ≥ 1008 logical px** — below that it's compact (icon-only + tooltip-on-hover). The app's default launch size must clear this or the nav pane looks perpetually broken. (`main.dart` sets `windowManager.setSize(...)` — keep it ≥ ~1180 wide.)
- **In compact mode, the nav item title is carried by `Tooltip.richMessage`, not a `Text` widget** — `find.textContaining()` won't find it there. For display-mode-independent integration tests, prefer asserting on the icon (`find.byIcon`) over the title text.
- **IconButton:** Does not support `tooltip` parameter — wrap in `Tooltip()` widget manually
- **ButtonSize:** `ButtonSize.small` is invalid — use default sizing only
- **ProgressRing:** No `width`/`height` params — wrap in `SizedBox.square(dimension: N)` instead
- **ToggleSwitch:** Exists in app bar but may be obscured by `WindowCaption` drag layer in tests — use `warnIfMissed: false` when tapping
- **NavigationAppBar / NavigationPane:** May not be directly findable via `find.byType()` in integration tests due to widget tree structure — prefer `find.byType(NavigationView)` or text-based finders instead
- **FilledButton:** Imported from both `fluent_ui` and `material` — avoid importing `flutter/material.dart`; use `flutter/foundation.dart` if needed

## WSL / Windows Subprocess Gotchas
- **`wsl.exe` does not exec the command you give it — it re-parses it through the distro's default shell.** `wsl.exe <options> <command…>` re-joins its argv into one string and hands that string to the distro's default shell, which parses it a *second* time, destroying one level of quoting. `bash -c '<script>'` therefore arrives as `bash -c <first word of the script>` (a throwaway child) with **the rest of the script running in the outer shell**. Measured live 2026-08-28: `bash -c 'X=hello; echo [$X]'` printed `[]`, and `$BASH_EXECUTION_STRING` came back as `bash -c echo …`. This is silent — it produced wrong *results*, not errors: `AiWorkspaceService`'s status probe `_s=$(…)` was permanently empty so the `running` branch was never taken for any tool, and `set -o pipefail` on installs never applied. When the command string contains a newline, the outer shell's failed re-parse is what surfaces as the user-reported `bash: -c: line 2: syntax error near unexpected token '2'`. **The fix is `--exec` (`-e`)**, which skips the default shell and execs argv intact.
  - **Never build in-distro `wsl` arguments by hand.** Use the two builders in `lib/api/wsl_args.dart`: `wslExecArgs(distro, argv, user: …)` when you have real argv, `wslShellArgs(distro, script, user: …)` when you have a shell *script* (pipes, `;`, `&&`, `>>`, `$(…)`, quoting) — the script is passed to `bash -c` as **one** argument. Both emit `--exec`.
  - **Never `splitShellArgs()` a command and append the pieces to a `wsl` argument list.** That is the worst of both worlds: the split strips the quotes and the re-join then feeds the unquoted result to a shell. `echo 'u ALL=(ALL) NOPASSWD:ALL' >> /etc/sudoers.d/x` came out the other side as a bash syntax error on the bare `(`.
  - **Legitimate exceptions**, all of which have *no* in-distro command to protect: host-level verbs (`--list`, `--import`, `--terminate`, `--mount`, …), where `--exec` is not even valid; interactive stdin-driven shells (`WSLApi.startShell`, `execCmds`' first spawn); and `WSLApi.start()`, which *depends* on the re-parse — its trailing `;/bin/sh` only becomes a second command because the default shell re-parses the flattened argv, and that is what keeps the terminal window open.
  - **`runInShell: true` is a second, independent mangling layer** on Windows: it wraps the call in `cmd.exe /c`, which consumes `&`, `|`, `<`, `>` and `^` before `wsl.exe` ever sees them. In-distro command invocations must pass `runInShell: false`.
  - **Remote WSL mode (`ssh host wsl …`) re-flattens argv a third time**, in `ssh` itself — and the shell that re-parses it on the Windows host is whatever OpenSSH's `DefaultShell` is: cmd.exe out of the box, PowerShell on most configured machines, sometimes Git Bash. **No quoting style survives all three.** POSIX single quotes (the old `quoteCommand: true`) made *every* remote command a PowerShell parse error (`Unerwartetes Token "'--list'"`, measured live 2026-09-05 against `Eric@WINDOWS-VM`, bostrot/ai-tasks#21); double quotes are stripped by powershell.exe's own argv parser before the PowerShell parser runs (sshd spawns `powershell -c "<command>"`), and `--%` sits behind that same parser. `lib/api/remote_command.dart` is the one answer: a command whose tokens are all *shell-neutral* (`[A-Za-z0-9_./:=+-]`, e.g. `wsl --list --quiet`) goes across bare; anything else goes as `powershell -NoProfile -NonInteractive -EncodedCommand <base64>` whose script starts the real program through `System.Diagnostics.Process` with a `windowsCommandLine()`-built command line (list2cmdline rules), inheriting stdio and propagating the exit code — verified byte-for-byte on the real host with quotes, `|`, `$`, `%`, newlines and doubled spaces. `_buildRemoteArgs` in `wsl.dart` and `mount_service.dart` both go through `remoteHostCommand()`; PowerShell scripts run on the host go through `_buildRemotePowerShell()` → `remotePowerShellScript()`, which also turns a terminating error into exit 1 with a plain-text message instead of CLIXML on stderr. Anything that is part of the *remote command* (VS Code's path, the `passwd` argv) must be in the argument list **before** `_buildRemoteArgs` is called — appended afterwards it lands behind the wrapper. The interactive terminal/editor launches (`start`, `openBashrc`, `startVSCode`, `exec`'s `passwd` branch) still build their `wsl` args by hand — they only pass simple flags, and they deliberately want the distro's default shell (see the exceptions above). `test/mocks.dart` unwraps the encoded form (`decodeRemoteCommand`) so its `bash -c` simulations keep working for remote targets; assert on the raw wire shape via `runCalls`/`lastRunArguments`.
- **`pkill -f` in a one-shot `bash -c` script kills the script.** `-f` matches the *full command line*, and the shell running the kill carries the whole script as its own argv. The `[h]ermes` bracket idiom shields only the pattern (`[h]ermes` is eight literal characters with no `hermes` substring in them) — it does nothing about a second, unbracketed mention of the same tool elsewhere in the string, which is what every one of these scripts has. Measured 2026-08-28 against the real distro: `pkill -f '[o]penclaw'` preceded by `openclaw gateway stop` exited 15 (SIGTERM) with no output, so Stop reported failure — with an empty message, because a signalled shell writes nothing to stderr — over a gateway it had in fact stopped; Hermes' start died before its `setsid` line and so could never start at all. **Use `_killByPattern()` in `lib/api/ai_workspace/service.dart`**, which lists candidates with `pgrep` and skips `$$`/`$PPID`. Keep that `pgrep` a *single* command: `$(pgrep …)` forks and execs `pgrep` directly, but `$(pgrep … | anything)` forks a real subshell that inherits the matching command line and becomes a target of the very loop that spawned it. Independent of the `wsl.exe` re-parse above — it reproduces with `--exec` in place and under a plain local `bash -c`.
- **`wsl.exe` output is UTF-16LE** — must be decoded as raw bytes with null-byte stripping (see `ExecutionBroker.decodeWslOutput`). Don't assume `stdoutEncoding: systemEncoding` works for `wsl` invocations.
- **`wsl.exe` error text is localized** (e.g. German on a German-locale Windows install) — never match stderr on English substrings like `"not found"`. Match on the stable WSL error *code* instead, e.g. `WSL_E_DISTRO_NOT_FOUND` — the `Wsl/Service/WSL_E_*` code suffix is not translated, even when the surrounding sentence is.
- **`wsl --install -d <name>` does not create a distro under a custom name** — `-d` there just targets an existing distro for other purposes; it's easy to misread as "install as \<name\>". To register a *new*, distinctly-named distro, use the positional + option form: `wsl --install <Distribution> --name <Name>`.
- **When launching an SSH command through a non-`ssh` executable** (Windows `start`, `wt`, `powershell -command`, anything where `ssh` isn't the process itself), the literal `'ssh'` token must be manually prepended to the argument list. Helpers like `_buildRemoteArgs()` in `wsl.dart` return only ssh's *options* (`-o ...`, target, subcommand) — they don't include the `ssh` executable name, because `_runWsl`/`_startWsl` pass `'ssh'` as the process executable directly. Any code that instead launches via `start`/`wt`/etc. must prepend `'ssh'` itself or the command silently launches garbage.
- **`ExecutionRequest.timeout` is enforced via `.timeout()`** in `ExecutionBroker.run()`, and the child *is* reaped on timeout — `run()` goes through `Shell.start`, so it holds a killable handle and runs it through `ExecutionBroker.terminate()` (SIGTERM, escalating to SIGKILL after 2s). That reaping is load-bearing: `list.dart` re-polls every 5s, and abandoning instead of killing leaked hundreds of orphaned `wsl.exe` processes. Anything that spawns via `startPersistent` owns its own child and must call `ExecutionBroker.terminate()` itself. Orphans still accumulate from crashed/interrupted debug sessions, and enough of them contend with each other and cause *cascading* unrelated failures (check `Get-Process wsl,wslhost` if WSL starts behaving erratically after heavy manual testing, and kill stragglers).
- **A distro can fail to start (`Wsl/Service/CreateInstance/E_FAIL`) purely from low host disk space** — always check `df -h /c/` (or equivalent) when a WSL start failure doesn't otherwise make sense.
- **WSL2's per-distro VHDX never auto-shrinks.** Deleting data inside a distro (e.g. `docker system prune`) frees space inside the distro's filesystem but does *not* reclaim host disk space — the dynamically-expanding `.vhdx` file stays at its high-water mark. Reclaiming it needs `wsl --terminate <distro>` then `Optimize-VHD -Path <path> -Mode Full` from an **elevated** PowerShell (Hyper-V module) — cannot be done from a non-admin context.
- Per-distro VHDX location/GUID mapping: `HKCU:\Software\Microsoft\Windows\CurrentVersion\Lxss` maps each distro's GUID subkey to its `DistributionName` and `BasePath` (under `%LOCALAPPDATA%\wsl\`).

## State Management Patterns
- `GlobalVariable` class in `helpers.dart` holds static state flags (e.g., `aiPanelVisible`, `testProEnabled` for forcing Pro in tests/dev without a real license)
- `prefs` is a global `SharedPreferences` instance — must be initialized before app build
- `LicenseManager()` is a singleton (`factory LicenseManager() => _instance`) — **never** wrap it in `ChangeNotifierProvider(create: (_) => LicenseManager())`. `Provider` calls `dispose()` on whatever `create` returns when the widget unmounts; since the "created" value is actually the shared singleton, this permanently breaks Pro-gating (AI chat, AI Workspace, anything checking `.isPro`) for the rest of the app session the first time the user leaves the License screen. Always use `ChangeNotifierProvider.value(value: LicenseManager())` instead — `.value()` does not take ownership of the instance's lifecycle.
- **Business model is a one-time purchase, not a subscription.** Two routes on Windows since bostrot/ai-tasks#37: the Microsoft Store (US$ 9.99, entitlement = MSIX package identity) and a licence key bought on `wslmanager.com` (US$ 14.99) for buyers who would rather skip the Store — the same shop and the same key macOS uses (US$ 19.99), validated through `licenseValidateUrl` and cached by `LicenseManager`. The route set per host lives in `lib/api/purchase_routes.dart` (`purchaseRoutesFor(apple:)`), not in the screen; `LicenseScreen` takes an `appleHost` test seam so either layout can be pumped from either dev machine. The key-entry box is shown on every host now, not just macOS. The rest of this bullet predates the key-based licence and is kept for the Store details: There was a Stripe-subscription experiment (test-mode only, never live); it has been fully removed — no license keys, no validation backend, no quota, no billing portal. If you find docs/comments referencing "monthly/yearly plans" or `n8n.aachen.dev` license endpoints, they're stale. `LicenseManager().isPro` = `hasLegacyPro || isStoreLicensed`. Store detection works via **MSIX package identity** (`GetCurrentPackageFullName` via package:win32 in `_detectStoreInstall()`): a Store install runs packaged, the portable GitHub build doesn't. Consequences worth knowing: (1) `flutter run`/`flutter test` and the Debug exe are unpackaged → never Pro locally; use `GlobalVariable.testProEnabled`, `claimLegacyPro`, or the `LicenseManager.storeInstallCheckOverride` test seam (a **static** on the singleton — always reset to null in tearDown). (2) A self-built/side-loaded MSIX also gets Pro — accepted, the repo is open source so gating is an honor-system nudge, not protection. (3) The release pipeline DOES attach an `-unsigned.msix` to GitHub releases — deliberately left that way: it's load-bearing (`publish-store.yml` downloads exactly that release asset to submit to Partner Center), and an unsigned MSIX can't be installed without self-signing anyway, so it doesn't meaningfully undermine the gate; the portable `.zip` and the Inno `-setup.exe` both run unpackaged → free tier, as intended. `init()` also deletes the old Stripe-era prefs keys (`LicenseKey`, `LicenseStatus`, …) as one-time cleanup.
- **Only the direct builds update themselves.** `lib/api/updater.dart`
  (`UpdateService`) asks the releases API for the newest tag, picks the one
  artefact the host can apply — the Inno `-setup.exe` on Windows, the
  `-macos.zip` (dmg as fallback) on the Mac — downloads it and hands it to the
  platform installer; `lib/dialogs/update_dialog.dart` drives it and Settings →
  Updates carries the auto-check toggle and a manual check. A Store install is
  `UpdateChannel.store` and is never offered anything: the Store owns the
  update and a packaged app cannot write into itself. The channel comes from
  the same MSIX package identity the Pro gate uses (`LicenseManager
  .isStoreLicensed`), so it is only meaningful after `LicenseManager().init()`
  — which `main()` awaits before `runApp`, i.e. before `initRoot` runs. Both
  install paths outlive the app that starts them, so they go through
  `UpdateService.launcher` (detached `Process.start`) and **not**
  `ProcessShell.start`, which adopts the child into the app's job object and
  would kill the installer the moment the app quits.
- `AiService` is a singleton for AI chat, powered **entirely by the user's own OpenAI-compatible key (BYOK)** — there is no app-operated AI backend and no query quota. `sendMessage()` throws `'pro-required'` without Pro and `'byok-required'` without a stored key; `hasByokConfigured` is a pure "is the key present" check (deliberately NOT Pro-coupled, so Settings can manage the key regardless of entitlement — the Pro gate lives in `sendMessage`/the UI, not in configuration state). There is no enable/disable toggle for BYOK anymore: with no backend, the key isn't an alternative route, it's the only one.
- `LicenseManager` also grants a permanent, honor-system "legacy Pro" to early purchasers via `claimLegacyPro(email)` (client-side only, not backend-verified — no way to cross-check Microsoft Store purchase records here — intentionally time-boxed via `legacyClaimWindowCloses`). `hasLegacyPro` reads straight from `prefs` on every access (not cached); when both legacy and store entitlements exist, `plan` reports `legacy`.
- App-wide long-running-operation feedback: `Notify.message(msg, {loading: true})` shows a bottom status bar with a spinner, callable from anywhere including service/API-layer code (not just widgets) — see `lib/api/ai_workspace/service.dart` for a multi-step example (distro setup → docker install → image pull, each with its own message)
- **Every `Notify.message` that reports an outcome must pass `severity:`.** Default is `InfoBarSeverity.info`, which is also what a failure used to render as — a blue info icon on the word "ERROR:". Pass `error` / `warning` / `success` and let the InfoBar carry it; do not put the severity back into the string. `notify.dart` re-exports `InfoBarSeverity` so an `api/` file can name one without importing fluent_ui.
- **A message with `loading: true` lives until something replaces it; everything else expires** after `notifyDefaultDuration` (8s) and is dropped on navigation. So a code path that starts a spinner owns clearing it on *every* exit — including the ones that only write to an inline banner. `Notify.message('')` is the way to take the bar down without saying anything (see `_failCreate` in `create_dialog.dart`).

## Architecture Notes & Known Gaps
- **In-distro config writes are read-modify-write and MUST stay serialised.** `WSLApi.updateWSLConf` / `removeSetting` / `updateDistributionConf` / `removeDistributionSetting` each read the whole file over `wsl.exe`, mutate the model and write it all back — a round trip of a second or more. The `wsl.conf` dialog and the package screen write **per key** (a debounce for a text box, the tap itself for a toggle), so two edits made inside that window used to both read the *pre-edit* file, and the second write put back a copy the first key was never in. It is silent: both writes succeed, the UI shows both values, and the file has one of them. Measured live 2026-08-28 against a real distro — `[network] hostname` typed 1.2s before a `generateHosts` toggle, and `[boot] protectBinfmt` set next to `[boot] command`, both vanished. All four entry points now go through `WSLApi._serialiseConfigWrite`, a **static** per-`'<distro>|<path>'` promise queue (static because `wslApiBuilder()` hands out a fresh `WSLApi` per write). Its tail deliberately swallows errors so one unreachable distro can't wedge every later write to it. Don't add a fifth read-modify-write path that bypasses it.
- **AI Workspace** (Hermes Agent, OpenClaw, Open WebUI, OpenCode) runs in a dedicated `ai-workspace` WSL distro, created via `wsl --install Ubuntu --name ai-workspace` and always driven as root (`-u root`) — it's automation-only, no interactive login, so there's no default-user setup to skip. It's Pro-gated (`lib/screens/ai_workspace_screen.dart`); non-Pro users get a paywall and the screen never touches WSL. Docker isn't preinstalled on the bare Ubuntu image — `AiWorkspaceService._ensureDockerReady()` installs `docker.io` via apt on first Docker-backed tool use. The service's `init()` is split into `seedToolStates()` (sync) + `ensureDistro()` + independent per-tool `refreshStatus()` calls specifically so a UI layer can render immediately and update each tool's card as its own check resolves, rather than blocking behind one page-wide spinner.
- **`AiWorkspaceService` is a single shared instance provided from `main.dart`** (via `Provider<AiWorkspaceService>`, constructed once alongside `ExecutionBroker`), not a fresh instance per screen mount like it used to be — the AI Workspace screen now does `context.read<AiWorkspaceService>()` instead of constructing its own. This exists so `main()` can kick off `ensureInitialized()` (memoized: `seedToolStates()` + `ensureDistro()` + `refreshStatus()` for every tool, gated on `LicenseManager().isPro` at startup, not awaited) in the background *before* the user ever opens the screen — the whole point being that opening AI Workspace shouldn't cost 2-3 fresh `wsl` round trips every single time. `ToolState.checked` (false until a tool's first `refreshStatus()` completes, set in a `finally` so it's true even on error paths) is what lets the screen tell "genuinely not checked yet" apart from "checked and confirmed not installed" — both start out as `ToolStatus.notInstalled`, so status alone can't distinguish them. The screen's `initState()` only shows a checking spinner for tools where `checked != true`; a tool the startup background check (or an earlier visit to the screen, since the shared instance persists across navigation) already resolved renders immediately, no WSL call. `_retryInit()` still forces a full recheck of everything regardless, by explicitly repopulating the checking set. If you construct `WSLManager()` directly without going through `main()` (tests do this), it falls back to building its own `AiWorkspaceService` — the same optional-param-with-fallback pattern `executionBroker` already uses.
- **Remote WSL control** (SSH into a *remote Windows* host, then run `wsl.exe`/PowerShell there — not SSH into a Linux distro) is implemented directly in `WSLApi`/`MountService` via hand-rolled `shell.run('ssh', ...)` calls, gated by `_useRemoteWsl` (reads `UseRemoteWSL`/`RemoteWSLTarget` prefs, validated via the shared `lib/api/remote_target.dart` — don't re-duplicate that regex, it used to be copy-pasted 3x and could drift). Settings UI: `lib/screens/settings_screen.dart`.
- **`RemoteShell`/`ExecutionBroker` are not actually wired up for remote WSL** despite `doc/remote-execution-architecture.md` describing that migration as "✅ Complete" — verify claims in that doc before trusting them. Every production `WSLApi()`/`MountService()` call site uses the default constructor (no `broker` passed), so the `_broker != null` branches throughout `wsl.dart`/`mount_service.dart` are dead code today; remote execution actually happens through the plain `shell.run('ssh', ...)` fallback paths.
- **macOS support (2026-08)** runs on a backend abstraction: `lib/api/vm/vm_backend.dart` declares the shared instance-lifecycle surface (`VmBackend`) plus a `VmFeatures` capability set; `WSLApi extends VmBackend` and `AppleVmApi` (`lib/api/apple/apple_vm_api.dart`) implements it by driving the bundled `vmctl` Swift helper (`macos/vmctl/`, Virtualization.framework — build/sign via `scripts/build_macos.sh`, Swift tests via `scripts/test_vmctl.sh`). Production code obtains the backend through `vmBackend()` in `lib/api/vm/vm_platform.dart` (test seam: `vmBackendBuilder`); never construct a backend directly in shared code. UI, navigation, settings sections, MCP tool registration and the template deprecation banner all gate on `vmBackend().features`, not on `Platform.isWindows` — remote WSL runs the WSL backend from a Linux host, so host-OS checks are the wrong axis. WSL-only MCP tools register only for `WSLApi`; the Apple backend adds `vm_*` tools (create/start/ip/import). `vmctl` keeps each running VM in a detached daemon process (SIGTERM = graceful stop), stores VMs under `~/Library/Application Support/WSLManager/vms` (or the app's DataPath), seeds a store-wide SSH key via cloud-init so `exec`/`shell`/templating work on cloud images, and resolves guest IPs from `/var/db/dhcpd_leases` by MAC. **A Linux guest is seeded with two keys and a password** (bostrot/ai-tasks#60): the store key *and* the Mac user's own `~/.ssh` public key — generating `~/.ssh/id_ed25519` when they have none, and returning nil rather than failing the create when `~/.ssh` is unusable — so a plain `ssh user@ip` from their own Terminal works; plus a generated console password for the seeded (non-root) account, kept in the VM's `config.json`, because cloud-init's `lock_passwd` + `*`-hash treatment left the login prompt on the VM's own screen unanswerable by anybody. `vmctl credentials` reads all of that back, minting the password and reseeding when the VM predates it (`appliedOnNextBoot` says the guest has not read it yet); the row's key button (`VmFeatures.guestCredentials` → `showVmCredentialsDialog`) is the only place the UI shows it. SSH stays key-only (`ssh_pwauth: false`) — the password buys a console login and nothing reachable over the network. The row's terminal button on a *running* VM now goes through `AppleVmApi.openTerminal`, which prefers an SSH shell as the VM's configured user and falls back to the serial console; the stopped-VM button is still the console, deliberately, because that is the path that watches a guest boot. Templates stay first-class on macOS (raw `.img` disk copies; `VmBackend.templateExtension`); the deprecation only applies to the WSL backend. Widget tests that assert WSL-specific UI must pin `vmBackendBuilder = () => WSLApi(shell: MockShell())` or they take the Apple path on a macOS dev host; tests needing real Windows path semantics are tagged `@TestOn('windows')` or `skip: !Platform.isWindows`. Building the app itself needs full Xcode; a CLT-only host can still run `flutter test`, `swift build` and the vmctl test script.
- **AI Workspace tool install URLs are real, verified third-party projects, not fixed forever**: Hermes Agent installs from `https://hermes-agent.nousresearch.com/install.sh` (real binary: `hermes`, real project: NousResearch/hermes-agent) and OpenClaw from `https://openclaw.ai/install.sh` (real binary: `openclaw`, real project: openclaw/openclaw). The *original* URLs here (`get.hermes-agent.dev`, `install.openclaw.ai`) were placeholders that never resolved — `curl -fsSL <url> | sh` silently exits 0 even when curl fails to resolve the host (empty stdin still makes the piped shell "succeed"), so every install of those dead URLs reported success while installing nothing, and the next status check correctly found nothing there and reverted to "not installed". `AiWorkspaceService.install()` now prefixes every install command with `set -o pipefail;` so a dead curl target can't masquerade as success again — preserve that prefix (or the equivalent) if you touch install commands. OpenClaw runs as a background gateway managed by its own CLI (`openclaw gateway install --force && gateway restart`). **Hermes does not**: `hermes gateway` is the *messaging* gateway (Telegram/Discord/WhatsApp) and binds no TCP port at all — the process that listens on 9119 is `hermes serve --skip-build`, which is what the card starts, kills (`pgrep -f [h]ermes.*serve`) and probes. Aiming the lifecycle at `gateway` meant Start could never go green and Stop reported success over a service that kept serving. Hermes also needs **`--skip-setup`** on the install: `--non-interactive` gates `prompt_yes_no` but not the setup wizard, which `main()` runs unconditionally and which reads `/dev/tty` directly — under `wsl.exe` the wizard-s own `(: </dev/tty)` escape probe *succeeds*, so it opened a terminal nobody was typing into and sat there until the silence budget reaped the install. With both fixes the whole lifecycle is **live-verified 2026-08-28**: install exit 0 in 244s unattended, start binds 9119 and answers HTTP 200 from Windows, stop frees the port and leaves no process. Uninstall must also `rm -f /usr/local/bin/hermes` — the installer writes that launcher as a wrapper *script*, not a symlink into the install root, so removing only the roots left `command -v hermes` answering "exists" over a tool that could not run. A live Hermes install (Python + Node + ffmpeg + an 8k-file git clone) is heavy enough that it briefly crashed WSL on a disk-constrained dev machine (`C:` at ~3.7GB free); recovered cleanly via `wsl --shutdown`, no data loss, but be aware these installs are not lightweight and don't repeat them carelessly on a low-disk machine. `_existsCheck()`'s `cmd://<binary>` scheme (`command -v <binary>`) replaced a per-tool `~/.foo` directory check for these two — that directory-tilde check is still used for any future tool that isn't docker- or PATH-based, but note `~` does **not** expand inside double quotes in bash (`[ -d "~/.foo" ]` silently always reports "missing" even when genuinely installed) — this is why the tilde-based check was wrong for hermes/openclaw in the first place.
- **OpenCode** (`AiWorkspaceTool.openCode`, real project: `anomalyco/opencode`, `https://opencode.ai/install`) is the fourth AI Workspace tool and needs two things the other three don't. **(1) `--port` is mandatory.** `opencode web`'s flag default for `--port` is `0`, i.e. "bind any free port" — omit it and the server comes up somewhere the card can never find, so `_kOpenCodePort` (4096, the port the project's own docs use in every example) is passed explicitly on every start. **(2) The installer hardcodes `$HOME/.opencode/bin` and offers no prefix flag or env override**, and it puts that directory on PATH by appending `export PATH=...` to a shell rc file — which nothing here ever reads, because every in-distro command runs through a *non-interactive* `bash -c`. So the install command passes `--no-modify-path` (no rc surgery to undo) and symlinks the binary into `/usr/local/bin`; that symlink is the only reason the `cmd://opencode` existence check can answer "exists". Uninstall therefore removes it explicitly, by hand rather than through the CLI's own `opencode uninstall` — a subcommand that wants to confirm before deleting is exactly the shape that goes wrong unattended, and a leftover launcher is exactly the failure already documented above for hermes. `web`, not `serve`: both start the same HTTP server, but only `web` serves the browser interface "Open Dashboard" opens. It binds `127.0.0.1` (OpenCode's own default) deliberately — the server is unauthenticated unless `OPENCODE_SERVER_PASSWORD` is set, and WSL localhost forwarding already makes a loopback bind reachable from Windows. The browser `web` tries to launch on start is harmless: OpenCode wraps it in `open(url).catch(() => {})`, so a distro with nothing to open just carries on serving.
- **The AI Workspace install path is streamed and bounded by *silence*, not wall clock** (`AiWorkspaceService._runStreamed`). A total-runtime cap cannot tell a slow install from a hung one: measured 2026-08-28 against the real distro, a cold Hermes install runs 482s and goes completely quiet for 306s inside one `npm install --silent` whose output the upstream script redirects to a temp file — so the old 5-minute wall-clock cap killed a *healthy* install every time, always mid-npm, leaving a half-built tree and no `hermes` binary. The budget is now 12 min with no output at all (it must stay above 600s: that is the upstream script's own per-step cap) plus a 45 min absolute ceiling. Every line that arrives resets the clock, on stderr as well as stdout, and `\r` counts as a line end so progress-bar redraws register as progress. The last line is exposed via `AiWorkspaceService.installProgress(tool)`; like `isInstalling()`, it survives navigating away from the page. For tests, `TestShell.processFactory` swaps in a `ControlledProcess` (test/mocks.dart) whose output and exit the test drives — `MockProcess` emits everything at once and has already exited, so it cannot express "still running, still printing".
- **"Open Dashboard" (`AiWorkspaceService.getDashboardUrl()`)** opens each running tool's web UI. Open WebUI is a bare static port (`ToolConfig.port` + `getUrl()`, no WSL round trip needed) — but Hermes and OpenClaw each need their own dashboard *server* explicitly started (`hermes dashboard` → `http://127.0.0.1:9119`; `openclaw dashboard` → `http://127.0.0.1:18789`, which prints a single-use pairing link rather than a bare URL), documented at their respective `docs.openclaw.ai/web/dashboard` and `hermes-agent.nousresearch.com/docs/.../web-dashboard` pages — not the same port as the `gateway` process. `ToolConfig.dashboardCommand` (null for Open WebUI and OpenCode, both of which are bare static ports) drives this: when set, `getDashboardUrl()` truncates a per-tool log file, spawns the dashboard command detached (`setsid ... & disown`, same technique as the gateway start commands), and polls the log for up to 5s for a `https?://` URL rather than assuming a fixed port — re-running the command is the documented, idiomatic way both tools expect you to "open or reopen" the dashboard, so it's safe to invoke on every click rather than trying to detect an already-running instance first. **Before returning that URL, `getDashboardUrl()` also polls it with a real HTTP request (`_waitUntilReachable`, injectable via the constructor's `reachabilityChecker` param for tests — never let this hit a real network stack in a unit test) for up to 10s.** This exists because `docker ps` reporting a container "Up" (or a gateway CLI printing its link) does not mean the web server inside has actually finished starting — without this, "Open Dashboard" would open a browser tab to a URL nothing was listening on yet, which renders as an empty response, not an error. Root-caused live on the dev machine: Open WebUI's container was found `Exited (255)` shortly after start, correlating with `C:` being critically low on free space (~3GB) — the same disk-pressure issue already diagnosed earlier for this container's startup (DB migration is write-heavy). That crash itself is an environment problem outside this fix's scope; what changed here is that the app now surfaces "couldn't open the dashboard" instead of a silent blank tab when it happens.
- **`AiWorkspaceService` persists each tool's last *confirmed* status/install path to `SharedPreferences`** (`AiWorkspaceStatus_<tool>` / `AiWorkspaceInstallPath_<tool>`, written by `_persistConfirmedState()`), so `seedToolStates()` can show a real answer on next app launch instead of a blank slate while `ensureInitialized()`'s background check re-verifies. `ToolState` has two independent booleans for this — don't conflate them: `hasKnownStatus` (true once there's *anything* real to show, cache or live — this is what the screen uses to decide spinner-vs-badge) and `checked` (true only once a *live* WSL check has completed this session — this is what gates whether a background refresh is still owed for that tool). A cache write only ever happens from a genuinely confirmed result — a successful command response, or an explicit "distro not found" WSL error code — never from a generic command failure or a caught exception, so a transient hiccup can't clobber good cached data with a wrong guess (`ExecutionBroker.run()` itself never actually throws — it always converts a shell-level failure into a failed `ExecutionResult`, so in practice both of those "don't persist" paths in `refreshStatus()` are reached via a non-zero exit code, not a raw Dart exception, despite what the `catch` block's placement might suggest). `_retryInit()` in the screen explicitly resets `checked` to false on every tool before re-running — otherwise a tool already verified earlier in the session would get silently skipped by the checked-gated background-refresh loop even on an explicit user retry.
- **Containers are a front end over the host's engine, not a runtime of our own** (`lib/api/containers/`, `lib/screens/containers_screen.dart`, `container_*` MCP tools — bostrot/ai-tasks#57). `ContainerService` shells out to whatever `docker` or `podman` is on the host's PATH (over SSH when remote WSL is configured, same `sshRemoteCommand` path as `MountService`); nothing is bundled, nothing is installed into a distro or VM, and a container started here is the same object the user's own `docker ps` shows. Both engines take the same `ps/start/stop/rm/logs/exec` argument shapes, so one service drives either and the engine is a *value* (`ContainerEngine`) rather than a subclass. **Containers deliberately do not go through `VmBackend`**: an instance is a machine the app owns for its whole life, a container is a process tree the engine owns, and folding them into one list would give "start" and "delete" two meanings each. That is also why they get their own pane destination instead of more rows on Home. `availableEngines()` caches its probe for the life of the service (`invalidateEngineCache()` on the screen's Refresh, so installing Docker while the app is open does not need a restart); "installed" means the binary answered `--version`, and a dead daemon surfaces from `list()` with the engine's own stderr instead of pretending nothing is installed. `listAll()` skips engines that fail so one uninitialised `podman machine` cannot hide Docker's containers, and reports *every* message when they all fail. Container names/ids are validated against `^[a-zA-Z0-9][a-zA-Z0-9_.-]*$` before reaching argv — nothing runs through a shell, but a name starting with `-` would otherwise arrive as another flag. The engine pin lives in prefs (`ContainerEngine`, absent = auto) and is set in Settings → Docker; auto prefers Docker, then Podman. Not implemented on purpose: creating containers, images, volumes, networks and compose — those are the engine's own CLI/Desktop surface, and this screen is about seeing and driving what already exists.
- **`WslMcpService`** (`lib/api/mcp/wsl_mcp_service.dart`) runs a Pro-gated local MCP (Model Context Protocol) server exposing the WSL API to external MCP clients (Claude Desktop, other agent tools) — think "openterminal, but for WSL distros". Two tool families: one-shot (`wsl_list_distros`, `wsl_run_command`, `wsl_stop_distro`) and persistent terminal sessions (`wsl_terminal_start/send/read/list/close`, backed by `WslTerminalManager` — see below). Deliberately excludes destructive/one-way operations (create, remove, export, move) from the MCP tool surface — those stay GUI-only where a human directly confirms them. Binds to **127.0.0.1 only** (never `0.0.0.0` — unlike the distro-sync server in `components/sync.dart`, which is intentionally LAN-reachable; this endpoint can run arbitrary commands and must never be network-reachable by default — see the Cloudflare Tunnel bullet below for the opt-in exception) on port 59133, and requires a locally-generated bearer token (shown once in Settings, `WslMcpService().token`) on every request. The underlying `HttpServer` reference is a **static** field (mirrors `Sync`'s `static late HttpServer server`) so every `WslMcpService()` instance shares the one real running server — tests that call `start()` **must** `tearDown` with `await WslMcpService().stop()`, or a "running" server from one test silently makes the next test's `start()` short-circuit via its own idempotency guard and never invoke that test's injected factory (`capturedHandler` stays null). The protocol core (`lib/api/mcp/mcp_server.dart`) implements only the synchronous request/response subset of MCP over JSON-RPC (`initialize`, `tools/list`, `tools/call`) — no SSE streaming, no resumable sessions — sufficient for "call a tool, get one reply" clients but not the full Streamable HTTP spec. When decoding `params`/`arguments` from a message map, don't use a rigid `as Map<String, dynamic>` cast — maps not produced by `json.decode` (e.g. Dart literals in tests) can have different generic parameters and throw; normalize via `Map<String, dynamic>.from(...)` instead (checked via `is Map` first).
- **`WslTerminalManager`** (`lib/api/mcp/wsl_terminal_manager.dart`) gives MCP clients persistent, session-based shell control (start a session, send input over time, poll for output, close it) as opposed to `wsl_run_command`'s one-shot exec. Built on `WSLApi.startShell()`, which spawns `wsl -d <distro> -u <user>` with **no trailing command** — the exact same "drop into the distro's default shell, read commands from stdin" primitive `execCmds()`/`runCmds()` already use elsewhere in `wsl.dart`, not a new way of talking to WSL. `WslTerminalManager`'s session map is owned by `WslMcpService` and is **static** for the same sharing reason as `_server`; `WslMcpService.stop()` calls `closeAll()` so disabling the MCP server can't leave orphaned WSL shell processes running. **Testing gotcha**: `test/mocks.dart`'s shared `MockProcess.exitCode` resolves to `0` immediately, which is fine for one-shot commands but wrong for anything simulating a long-lived session (`WslTerminalSession`'s constructor does `process.exitCode.then((_) => _closed = true)`, so a session backed by `MockProcess` looks "already closed" almost immediately) — use a dedicated fake process with a `Completer`-backed `exitCode` that only resolves when the test wants it to (see `test/wsl_terminal_manager_test.dart`'s `_FakeProcess`) instead.
- **`CloudflareTunnelService`** (`lib/api/mcp/cloudflare_tunnel_service.dart`) is the opt-in exception to "MCP server never leaves 127.0.0.1": it runs a `cloudflared` quick tunnel (`cloudflared tunnel --url http://127.0.0.1:59133`, no Cloudflare account needed) to get a temporary public HTTPS URL, gated behind the MCP server itself being enabled first. Once this is on, the bearer token is the *only* thing protecting the endpoint from the entire internet — the Settings UI shows a persistent warning `InfoBar` for this reason, and `WslMcpService.stop()` also tears the tunnel down (a public URL routing to a dead server is worse than no URL). `cloudflared` is located via (in order) a previously-downloaded copy cached under `getDataPath()/bin/cloudflared.exe`, then PATH, then downloaded fresh from Cloudflare's official GitHub releases — same static-field sharing pattern as `WslMcpService`/`Sync`. **Never live-test the download/spawn path carelessly**: a real `cloudflared` invocation pulls a ~30-40MB binary and spawns a real outbound connection — for tests, always inject `binaryLocatorOverride` and `processSpawner` (see `test/cloudflare_tunnel_service_test.dart`) rather than exercising the real thing, and the integration test for the Settings toggle (`integration_test/mcp_settings_test.dart`) deliberately verifies the UI renders without ever tapping the toggle itself.
- **Cloud deploys ship the root filesystem, not the disk** (`lib/api/cloud/`, `lib/screens/cloud_screen.dart` — bostrot/ai-tasks#62). The obvious design does not work: a local instance's disk is not partitioned the way a provider's firmware expects, carries no virtio drivers and runs no cloud-init, so uploading one produces a machine that never answers and a bill that keeps running. What *is* portable is the filesystem, so a deploy is `wsl --export --format tar` → create a stock server whose cloud-init installs only Docker → `docker import` + `docker run … sleep infinity` there, and a pull back is `docker export` → `scp` → `wsl --import` under a **new** local name (importing over the source would destroy whatever the user did locally in the meantime). Gated on `VmFeatures.rootfsExport`, not on the host OS. **Both shipped backends set it** (#62, reopened): WSL hands over a tarball directly, while the Apple backend cannot — `vmctl export` writes a raw bootable disk, with a partition table and an EFI system partition, which `docker import` cannot read — so `AppleVmApi.exportRootfs` tars the *running guest's* `/` over the SSH path `vmctl exec` already owns, streamed straight to a file (a 20 GB system never becomes a string), starting the VM headless first and stopping it again if it was not running. Coming back is the asymmetric half: a bare rootfs has no kernel or bootloader, and Virtualization.framework boots through EFI, so `AppleVmApi.importRootfs` **clones the VM the deploy came from** (`sourceInstance`, which must exist and be stopped — `vmctl export` refuses a running guest), boots the clone and unpacks the archive over it with `/boot` and `/lib/modules` excluded, so the kernel that comes up is the one that already worked on exactly that disk; a clone left half-restored is deleted rather than handed over. Mount points are *emptied*, not pruned (`--exclude=./proc/*`, never `./proc`) — a container with nowhere to mount `/proc` fails its first `ps` — and every exclude is single-quoted because `vmctl exec` hands the command to the guest's shell, which would otherwise glob `*` against root's home. `--unlink-first` is used only when the guest answers `tar --version` with GNU tar; busybox rejects the option, and without it extracting over a running `/usr/bin` is `ETXTBSY`. `VmFeatures.rootfsImportNeedsBase` is what makes the pull-back dialog say all this. The whole *destination* is gated on `rootfsExport` too — unlike Containers and Kubernetes, which appear everywhere — because a Cloud screen that cannot deploy is a server list with a delete button, i.e. the second control panel for somebody else's product this app deliberately does not build; the route stays registered for deep links. It is the **last** pane entry on purpose: the pane holds seven items at the 800x600 the macOS walkthrough runs at, so whatever sits last is what a user at that size scrolls for, and Add instance and the AI Workspace are not entries to hide. **The SSH here is not `sshRemoteCommand`** — that one wraps commands for a remote *Windows* login shell; a Linux cloud host gets `posixQuote`/`cloudSshCommand` instead. `cloudSshOptions()` also deliberately does **not** reuse `getSshClientOptions()`: that pins one fixed `ControlPath` with no `%h` in it, so a master already open to the remote Windows target would swallow these commands, and OpenSSH takes the *first* value for an option, so appending an override cannot undo it. It adds `StrictHostKeyChecking=accept-new`, without which every first command against a minutes-old server fails under `BatchMode=yes`. The provider layer (`CloudProvider`, `HetznerProvider`) is the one place in the app that speaks a REST API instead of shelling out to the user's own CLI — `hcloud` is not installed on anybody's machine the way `docker` and `kubectl` are, and the credential is a token the user pastes (prefs `CloudProvider`, `CloudToken_<id>`) rather than a config the provider's tooling already holds. The instance a deploy put on a server is recorded as a *label on the server* (`wslmanager-instance`), not in prefs, so the pairing survives a reinstall and a second machine with the same token sees it too; that label is what makes the row offer Pull back. Cheapest-location monthly prices are shown on every row on purpose — a forgotten server is the expensive mistake this screen can cause.
- **`WebDashboardService`** (`lib/api/web/web_dashboard_service.dart`) is the Pro-gated browser dashboard on port **59134**, and — unlike the MCP server — it **binds `0.0.0.0` on purpose**: being reachable from a phone on the LAN is the feature. Every request (the page too) must carry the token, accepted as `?token=` (what the QR code / shared link encodes, so a scan is enough), `X-Dashboard-Token` or `Authorization: Bearer`; compared constant-time; prefs `WebDashboardEnabled`/`WebDashboardToken`. The page is one self-contained HTML document embedded as a Dart string (`lib/api/web/web_dashboard_page.dart`, no external assets so it works offline on a LAN); it drives the backend through `POST /api/tools/<name>` over the **same `buildWslMcpTools()` set the MCP server exposes** (destructive tools stay behind their confirm flags, and the page adds its own confirm dialogs), plus a thin REST layer (`GET /api/state`, `POST /api/instances/<n>/start|stop|copy`, `POST /api/shutdown`) for the cards. "Start" deliberately does **not** call `VmBackend.start()` — that opens a terminal/VM window on the host nobody is sitting at — it runs a no-op command (WSL) or `startHeadless` (Apple). The server handle and the terminal-session manager are static like `WslMcpService`'s, so tests must `tearDown` with `WebDashboardService().stop()`; `setEnabled(true)` resets the pref to false when the bind fails so a taken port isn't retried at every launch. `lanAddresses()` comes from an injectable `NetworkInterfaceLister` (never enumerate real interfaces in a unit test). QR codes come from `qr_flutter` and are always black-on-white regardless of theme. **`CloudflareTunnelService` is keyed by local port** (`localPort` constructor arg, default 59133 = MCP; the dashboard uses `CloudflareTunnelService(localPort: WebDashboardService.port)`), so the MCP tunnel and the dashboard tunnel coexist and stopping one leaves the other alone — `start()` takes no port argument any more. Settings UI: `_buildWebDashboardSettings` in `settings_screen.dart`, test keys `test-web-*`; the integration test (`integration_test/web_dashboard_settings_test.dart`) really binds the port but, like the MCP one, never taps the tunnel toggle.
- **Snippet sharing signs in with GitHub's device flow, which takes a client id and no client secret** (`lib/api/github_publish.dart`). The id is public information: the "WSL Manager" app's id (`9c2cbef8ac5d26ec745b`) is bundled as `kDefaultGithubClientId`, and `--dart-define=GITHUB_CLIENT_ID=...` overrides it when non-empty (an empty define, which the release scripts pass while the optional repository variable `WSLMANAGER_GITHUB_CLIENT_ID` is unset, keeps the bundled id). A client *secret* must never be shipped, because anything in a distributed binary can be extracted from it — GitHub classes desktop apps as public clients for that reason; a test asserts nothing secret-shaped is compiled in. The OAuth app's **Enable Device Flow** box must be ticked or every sign-in fails with `device_flow_disabled` (it was still unticked on 2026-09-04). Setup, verification `curl`, and the browser-MCP steps: `doc/github-oauth-setup.md`.
